## Product journey and release cuts

The sequence below is the target journey. Steps 4 and 5 require the parked MCP purchase tools and the proposed result contract from merged #89 to be implemented. They describe no current buying or payment capability.

1. The customer chooses a shopping agent in Viseca+ or connects Leash MCP in an external client. The agent pairs with the Wallet and receives only account-scoped tools. External clients choose a connector through their own host UI; Leash cannot provide a universal `/mcp` selector.
2. Before searching for products, the agent briefly clarifies the task, spending ceiling, permitted sellers or categories, occurrence limit and any essential unknown terms. It offers detail when requested. It proposes an enforceable draft and labels a model or service requirement it cannot verify as an open question. The trusted Wallet reads the saved draft from the backend, and the customer submits that draft's version and hash for confirmation. A v1 hash covers instruction, rules and uncertainty policy; a v2 hash also covers authored boundary cases. Neither hash binds the display-only examples or open questions.
3. Only after `get_policy_status` reports `confirmed` and a `mandate_id` does the agent search. An external agent's independent browser is outside the MCP server's control, so the phase order is guidance until a controlled Harness or search gateway enforces it. The future `buy` implementation must reject purchase requests without a paired principal and confirmed mandate. Today's parked `buy` rejects every request.
4. In the target purchase flow, the agent submits the selected merchant, product identity, cart, quantity and final all-in amount for a decision. Deterministic rules are authoritative. Merchant text and agent-supplied claims cannot change the policy. Unknown facts follow the confirmed uncertainty setting; a `fact_conflict` produces `step_up` even when that setting is `approve`. A pending `step_up` switches the in-app Harness to the trusted Wallet for that exact authorization. The agent resumes only after the backend records the customer's answer or the timeout.
5. In the target purchase flow, a final approval yields a processor-consumable authorization result and reference. An external payment processor decides how to complete payment. Leash does not implement the processor or claim that an approved decision means an order was placed or charged. A declined or pending purchase produces no payment authorization.

**10:00 CEST readiness checkpoint:** freeze a reviewed, model-off checkout; finish one real paired MCP and Wallet rehearsal without claiming a simulator outcome; obtain the human `strict` or `ask` decision for labels and generate the report; have the API, MCP endpoint, runner, shared store, Wallet operator and recording procedure ready. The reserved 10:30 to 10:50 live slot occurs after this checkpoint. The Harness, MCP buying and trained models have no verified 10:00 completion path and must not be represented as working there.

**12:00 expert submission:** demonstrate the live Viseca challenge API using a paired policy proposal, trusted Wallet confirmation, deterministic runner decision and one actual human Wallet step-up when the scenario produces one. Record the actual outcome. Show the 45-attempt replay and a report with reconciled labels if the human choice landed. Repeat the complete flow with a fresh mandate before claiming repeatability. If a planned outcome does not occur, report the observed one.

**17:30 final submission:** incorporate expert feedback and reviewed fixes on main. Work on the later capabilities may run concurrently in separate branches and merge continuously after exact-head review. Their inclusion in a submission depends on observed behavior, not the calendar. Keep the live model-off demo stable while independent work proceeds.
