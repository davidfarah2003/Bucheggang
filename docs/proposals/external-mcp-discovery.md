## Pairing and handoff boundary

The merged contract at `docs/contracts.md:377,397-400` says `begin_pairing` returns a `wallet_url` made from configured `LEASH_APP_ORIGIN` and a pairing code. The agent keeps the verifier private. A customer opens that link or types the code in the Wallet Pair screen, reads the agent label, scopes and expiry, then approves there. `complete_pairing` uses the code and verifier to return a scoped revocable agent token once. The agent then calls `get_policy_authoring_instructions` and `propose_task_policy`, waits for `get_policy_status` to say confirmed, and only then uses the opaque mandate ID. `buy` and `get_purchase_status` remain parked (`docs/contracts.md:397-404`). No token, verifier or policy-confirmation action belongs in the Wallet link.

The contract change for `wallet_url` and typed-code entry merged in #99 at `c2d39f6`. The MCP server now constructs that URL from its configured origin in `src/leash/policy/mcp_server.py:273-300`, verified by disposable real stdio and HTTP MCP clients in `docs/plans/01-policy-confirmation.md:124`. This proves the server's response shape on those transports, not a Codex, Claude Code or ChatGPT handoff. The Wallet's typed-code entry is separate app work. `docs/mcp-client.md:43,73-75,94-96` describes the handoff and host deployment; oskar1 owns its client-specific setup instructions. The end-to-end external client handoff remains unobserved.

`LEASH_APP_ORIGIN` must be a trusted Wallet origin reachable by the customer's device. A loopback Wallet address works only when agent client and customer browser share that host. For a remote client, the contract requires a trusted Wallet deployment; it rules out deriving the Wallet URL from a request Host or exposing the Wallet through an ad hoc tunnel (`docs/contracts.md:377,397`). The MCP transport address and the Wallet address have different roles. Browser approval authenticates the customer; it cannot be inferred from the agent receiving a code.
