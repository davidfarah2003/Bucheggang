This implementation is isolated from the live demo. Runtime source checkpoint `17d15fca841238c1ac56766565f1e9de7fc26272` adds startup selection, required model dependencies and a shared monotonic decision budget. It changes only runner code. The classifier producer and pure engine were not edited.

## Configuration

`leash.runner.settings` reads `LEASH_ENABLE_MODELS` from the process environment. Unset or `0` selects the existing pure engine. `1` is explicit model opt-in. Every other value raises `SettingsError`.

Opt-in also requires `LEASH_MODEL_MANIFEST` naming an existing manifest file. Startup loads the actual behavioural artifact and both-pack history, checks the artifact, split manifest, feature names and library versions through the producer's loader, and obtains the scoped OpenRouter credential through `load_openrouter()`. Missing configuration or dependencies raise. Nothing switches to another model or to model-off after a failure.

The required classifier package/artifact is a separate lane dependency and is absent from this branch's main baseline. Enabling the flag without that package raises a named startup error. The isolated verification used the reviewed producer at `e4ba7ba1f0707164ddfd6071779501a880598b44`. It is a two-revision composition, not an integrated model-enabled release.

Both the CLI and the API's `StepUpBook` select their evaluator at startup. The CLI uses that same evaluator for new decisions; the book uses it for customer-approval rechecks. The processes must use matching startup configuration and the same checkout/store. There is no new history-only flag. The separate history-only runner hookup remains deferred by the owner until after 17:30.

The behavioural artifact remains evaluation-only. The runtime rejects `escalation_fired=True`; no operating threshold was chosen. This check is not a claim of cryptographic authenticity for model output. The broader M4 output-integrity review remains open.

## Decision and deadline behaviour

An automated decision starts with one monotonic allowance derived from its original deadline minus 250 ms. Lock acquisition, policy refresh, extraction, evaluation and the submission deadline all consume that allowance. The budget also caps against the wall-clock deadline. Converting its remaining time for an HTTP call cannot extend the monotonic allowance.

An already-handled expired delivery retains #72's separate, bounded lookup. The expired budget still refuses a new decision. No old delivery gets a new submission window.

Extraction keeps the existing 1.5-second cap. Model-enabled processing reserves a second for assessments plus two seconds for later work before extraction starts. Required assessment work has a one-second cap under `asyncio.timeout_at`, including the producer's HTTP stream and parsing. The producer's own conservative deadline reserve also remains in force. An execution-only event copy tightens the producer deadline to the stage allowance plus that reserve, capped by the overall budget; this lets its pre-dispatch check reject time consumed by local scoring. Authorization, policy and history bindings are unchanged. CPU work and the pure composition result are checked against elapsed time before a result can leave the evaluator.

The pure engine checks the purchase before scoring. A conclusive deterministic failure returns its decline without calling models, as allowed by the design's execution order. This occurs before any provider attempt. A failed provider call propagates its error and never returns that earlier baseline as a replacement.

A customer-approval recheck uses the separate human deadline, with the same startup evaluator and guards. It removes the pending ID only from a copied checking state. Current hard failures and newly introduced uncertainties retain the existing answer rules. No answer is generated by the runner.

Running Python work cannot be forcibly cancelled by `Future.cancel()`, and executor shutdown can still wait for a running function. Filesystem writes are not preemptible. Durable recording of an accepted result remains required even if local I/O runs late. These limits remain visible; the implementation does not claim a hard real-time filesystem guarantee or a completed live end-to-end timing exercise.

The actual pinned provider response arrived in 494 ms and supplied activity probabilities unusual 0.16, unclear 0.02 and ordinary 0.81, sum 0.99. Zero paired rows completed, and no baseline or other replacement decision was returned. No request was retried. [Captured failure evidence](runner-model-runtime-2026-09-25-failure.json) names the revisions and response.

This final-source failure supersedes any suggestion that the earlier 13 successful calls established provider readiness. It also observes the required failure path with a real malformed response on an otherwise approvable input.
