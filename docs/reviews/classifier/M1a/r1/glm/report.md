## Findings

**G1 (blocking for a different scope, non-blocking here; recorded so it cannot be silently inherited).** M1a's grade is explicitly cut-scoped, and the m1-report's own Limits paragraph says P1/P2 engine integration is still needed before a model assessment can affect `evaluate()`. If M1 is later declared complete on the strength of this APPROVE alone, that is an unsupported claim: `src/leash/engine/evaluate.py` in this target still takes no assessment argument (verified: no classifier import in `src/leash/engine/evaluate.py` at 1f5a45d) and no live path calls the classifier. Failure scenario: an M1 "complete" declaration without the P1/P2 PR leads the team to believe history features inform live decisions when nothing changed in the deployed evaluator. This is why the verdict binds to the cut, not the milestone.

**G2 (medium, M2-facing, must be fixed before fitting).** `initiator_type` domain mismatch: both packs contain `human`, `agent` and `merchant` (verified counts: base 4112/453/53, additional 121059/19037/1904 rows respectively). `src/leash/engine/classifier/history.py:175` accepts only `{"agent", "human"}` and raises `unknown initiator type` on anything else. For purchases this is currently unreachable (all `merchant` initiators are refunds; all purchases are agent/human), so no shipped path fails today. Failure scenario: a future pack revision (or an M2 preprocessing change that passes non-purchase rows through `_features`) containing a merchant-initiated purchase makes `historical_purchases()` raise mid-corpus and the whole M2 fit aborts on one row. Also the schema doc `docs/eval/classifier/feature-schema.md:23` says the historical rows "carry their own pre-event limits and card_status" — the card_status acceptance set at `history.py:173` is `{active, blocked, expired}` matching the packs (verified), fine for now.

**G3 (low, documentation).** `docs/eval/classifier/feature-schema.md:3` and `history.py` correctly document strict `(timestamp, authorization_id)` pre-event ordering, but the replay-input side has an uncovered edge: `scripts/classifier_replay.py:79-81` checks only that scenario timestamps are non-decreasing across the 12 SCEN0002 rows, not that `(timestamp, authorization_id)` is strictly increasing. In the current pack the check holds (I verified 0 ordering violations among SCEN0002 rows with the documented key), and live events are protected by `for_event`'s digest binding, so no data today triggers it. Failure scenario: a scenario pack with two attempts sharing one timestamp and replay-order putting the higher `authorization_id` first would silently exclude that earlier attempt from the second attempt's features (strictly-less semantics), while the ledger state still records both. Cosmetic today, worth a strict-key check when the runner hookup lands.

Live `recent_attempt_count_10m` kept out of predictors. Historical velocity and run-level velocity remain separate features.
